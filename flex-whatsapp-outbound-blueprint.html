Agent-Initiated WhatsApp Outbound For Flex

A reference architecture for giving Flex agents a first-class WhatsApp outbound workflow: pick an approved template, pre-populate recipients from the active task, choose how a reply should route, and keep every open conversation visible in a side-nav panel so no customer thread quietly disappears.

Business outcomes
  • Agents can reach customers who did not pick up a call
  • Replies route back without manual re-assignment
  • Fewer orphaned conversations, visible to the whole team
  • 24-hour WhatsApp window is enforced, not accidentally broken
Why not just use the chat composer? Flex's chat canvas works once a conversation already exists, but it does not handle template picking, variable substitution, deferred-task routing policies, or re-engaging customers whose 24-hour window has closed. This blueprint fills those gaps while keeping Flex, TaskRouter, and Conversations as the system of record.

Why It Matters

Business Benefits

Outbound WhatsApp is often an afterthought in a Flex deployment: inbound traffic works because Studio and the Interactions API handle it, but reaching a customer first — especially after a missed call — is a manual, error-prone chore. This blueprint turns that into a one-click agent action with proper governance.

Reach Customers Who Didn't Pick Up

Agents can send a WhatsApp template directly from the active task context, with the customer's number pre-populated.

Route Replies Deterministically

Pick at send time whether a reply should come back to the original agent or hit the queue — enforced by the TaskRouter workflow.

No Lost Conversations

A side-nav panel shows every conversation an agent currently owns, plus a toggle to see the team's open conversations.

Guarded 24-Hour Window

A service pre-webhook blocks free-text sends outside the WhatsApp session window and prompts the agent to send a template to re-engage instead.

Pragmatic scope: this is a Flex-side agent workflow, not a replacement for Meta's Business Suite. The plugin handles the agent-critical moments; WhatsApp Business Platform and Twilio Conversations remain the system of record for messages and templates.

What It Does

Capabilities

Routing Policies

The Three Send Modes

Every outbound send is one of three modes. The mode is written to conversation attributes at send time and re-read by the lifecycle webhook when the customer replies, which decides how to spawn the resulting task.

Send & Open Chat

Immediate chat task on the sender's desktop. Uses the Interactions API with worker_sid, so the sender gets a direct reservation. Free-text is still blocked by the 24-hour window pre-webhook until the customer replies — the agent can send further templates in the meantime, and the chat composer unlocks the moment an inbound message lands.

Send — Reply To Me

No task on send. On customer reply, the lifecycle webhook sets KnownAgentRoutingFlag and routes via the workflow filter back to the sender.

Send — Reply To Queue

No task on send. On reply, a raw TaskRouter task is created without worker_sid, letting the workflow route it to any available agent in the queue.

Fallback policy is per-business: the plugin ships with a straight-forward Known Agent filter. Production deployments can extend the workflow with timeout-based fallbacks, skills, or availability expressions without touching plugin code.

Lifecycle

Park And Reopen

Parking lets an agent step away from a conversation without ending it: the Flex task is completed and the row returns to the Open conversations panel, but the Twilio conversation stays active and the Interaction channel stays bound. On the next customer reply (or an explicit reopen) a new task is reserved via channels.invites.create on the existing channel — no new conversation, no history loss.

  1. Park closes the agent participant, not the channel. Closing the channel would cascade to closing the conversation; closing the participant completes the task without that side-effect.
  2. Reopen reuses the existing Interaction channel. The Flex Invites API takes workflow + attributes but rejects both worker_sid and queue_sid — agent targeting goes through task attributes read by the workflow filter.
  3. Reopen-with-template picks the Outbound tab back up. When the 24h window has closed or the customer never replied, the plugin pre-populates the composer with the customer address and the existing conversation SID so the send reuses the same thread.
  4. Inbound-first conversations are backfilled on park. Studio-created conversations lack plugin attributes; park detects this, derives the customer address from the participant, attaches the lifecycle webhook, and lifts the conversation into the Open conversations panel.

Policy Guard

24-Hour Window Enforcement

WhatsApp allows free-text responses only within 24 hours of the customer's last inbound message. Outside that window, only pre-approved templates are permitted. The plugin enforces this at the service pre-webhook layer so an agent cannot accidentally bill a customer-service message as a template send.

1

Agent types free-text in the chat canvas

Flex calls the Conversations API. The service's pre-webhook on onMessageAdd fires before the message is persisted.

2

Pre-webhook evaluates the WA window

Fast-paths: non-WA, inbound, templates (ContentSid present), and non-plugin conversations pass through unmodified. For WA free-text, the webhook reads lastReplyAt from Sync.

3

Reject with wa_window_closed

If no reply has ever been recorded or the last reply is > 24h ago, the webhook returns HTTP 403 with a structured reason code. The message is never sent.

4

Plugin intercepts the Flex send-fail notification

A notification wrapper detects any send-fail toast whose task is a WhatsApp conversation and surfaces our own prompt: Reply to me / Reply to queue.

5

Agent picks a reply mode

Agent picks a routing mode; the plugin parks the current task with that mode, stashes a reopen context, and navigates to the Outbound tab with the customer address pre-filled.

Error handling is three-way, not uniformly permissive: transient Sync failures (5xx, network, auth) let the send through so an infra blip doesn't block valid traffic; a missing SYNC_SERVICE_SID returns a 500 so a deploy issue surfaces immediately; a missing Sync row is treated as "customer never replied" and the send is rejected. The lifecycle webhook upserts the Sync row on 404, so a dropped send-time write is self-healing as soon as the first delivery or reply event lands.

State Model

Tracking: Sync Today, Database Tomorrow

Each agent has a per-worker Sync Map keyed by conversation SID; a shared team map mirrors every entry for the "All agents" toggle. The plugin subscribes to the maps via the Sync JS SDK and renders a live list with status, last reply preview, and action buttons.

Trade-Offs

Key Design Decisions

The choices below shape how the plugin behaves across routing, lifecycle, and policy. Each card describes what the plugin does and why that decision was made.

Routing Replies Back To The Original Agent

Replies are routed via a declarative TaskRouter workflow filter that reads the sender's worker ID from task attributes. Keeps the routing policy in one place and matches TaskRouter's native model. The baseline filter has no built-in fallback — add a timeout + overflow queue in the workflow definition if your deployment needs one.

Parking Without Ending The Conversation

Park removes the agent from the Flex Interaction while leaving the underlying Twilio conversation active. The task is completed but the conversation stays available for a future reply or an explicit reopen, preserving history.

Reusing The Same Conversation On Reopen

Reopening a parked or stale conversation adds a new agent to the existing Interaction rather than creating a new one. The customer sees one continuous conversation, and the agent lands on the full history on their desktop.

"Reply To Queue" Without First-Refusal

When the agent chooses "reply to queue," the resulting task is created without any specific worker reserved first. Any available agent in the queue can accept, with the conversation context carried on the task so the chat panel renders correctly on acceptance.

Enforcing WhatsApp's 24-Hour Window

WhatsApp blocks free-text sends more than 24 hours after the customer's last inbound message. A Twilio-side check enforces the window on every outbound message so an agent can't accidentally violate policy, with inexpensive short-circuits for traffic the plugin doesn't own.

Catching The Failed Send In The UI

When the 24-hour check rejects a send, Flex shows a generic failure toast. The plugin replaces that toast with a specific prompt — "send a template to re-engage?" — so the agent gets a clear next action instead of an unexplained error.

Deployment Knobs

Configurability

Every value a deployment is likely to change at install time is exposed as an environment variable. Workflow routing rules and template content stay out of env — those live in TaskRouter and the Content Template Builder respectively. The 24-hour window itself is configurable via WA_WINDOW_HOURS but defaults to the standard WhatsApp Customer Service Window of 24 hours.

Serverless (serverless/.env)

Variable Default Purpose
AUTO_CLOSE_AFTER P5D ISO 8601 duration passed as Timers.Closed on every conversation. Resets on activity. Twilio enforces a 10-minute minimum.
WA_WINDOW_HOURS 24 Threshold the pre-webhook uses to block free-text sends. Change only if your messaging policy diverges from Meta's standard Customer Service Window.
SYNC_TOKEN_TTL_SECONDS 3600 Lifetime of Sync access tokens minted for the plugin. Short = tighter rotation; long = fewer token mints.
TASK_CHANNEL_NAME chat TaskRouter channel used when creating chat tasks. Only change if your workspace defines a custom channel.

Plugin build-time (plugin-whatsapp-outbound/.env, FLEX_APP_*)

Variable Default Purpose
FLEX_APP_FUNCTIONS_BASE_URL — URL of the deployed serverless; required.
FLEX_APP_SIDE_NAV_LABEL WhatsApp Outbound Label shown on the Flex side-nav item.
FLEX_APP_ENABLE_TEAM_VIEW true Expose the "All agents" toggle in the Open conversations panel. Set false for privacy-sensitive deployments.
FLEX_APP_ENABLE_PARK true Expose Park (me) / Park (all) on the task canvas. Set false for fire-and-forget deployments; Flex's native End button stays in place.
FLEX_APP_DEFAULT_SEND_MODE open-chat Which of the three send-mode buttons sits first in the composer. Agents can still pick any of the three per send.
FLEX_APP_WA_WINDOW_HOURS 24 UI threshold used to decide "Reopen" vs "Reopen with template" on each row. Must match the serverless WA_WINDOW_HOURS or UI and policy drift.

Intentionally not exposed: the pre-webhook on/off switch and workflow fallback rules. Letting a deployment turn the 24h guard off invites Meta-policy violations; routing logic belongs in TaskRouter workflow filters, not plugin env vars.

Shipping It

Production Readiness Checklist

The reference implementation is deployment-ready as a POC and demo. The items below are the realistic hardening work before using it at scale with real customer traffic.

  1. Move tracking off Sync-only. Add a database write alongside the Sync write for reporting and cross-agent search. Sync works for the real-time per-agent view and should stay; adding a Postgres or DynamoDB write to the same Functions is a small change that unlocks aggregate queries.
  2. Scope the team view by Flex role. "All agents" is open to every agent today. Gate server-side by Flex role (admin / supervisor) and route queries through the backend rather than exposing per-agent Sync maps directly.
  3. Add webhook retry / DLQ. If the lifecycle webhook fails once, the task is never created and nothing retries. Introduce an outbox table, exponential retry, or Twilio Event Streams forwarding so missed events are caught and replayed.
  4. Tune the TaskRouter workflow per business. The baseline Known Agent filter has no fallback expression. Production workflows typically add a timeout, availability check, or skills-based fallback before dropping to the default queue.
  5. Treat the pre-webhook as shared infrastructure. It fires for every message in the Flex Conversations service. Benchmark it under production load, add structured logging, and consider owning it from a longer-lived service rather than a serverless function if cold-start latency is a concern.
  6. Observability. Pipe serverless logs to a sink that supports search and alerting (Twilio Event Streams → Kinesis/EventBridge or a direct push to Datadog). Add success logs — the current functions log on error only, which makes debugging ambiguous.
  7. End-to-end tests. No automated tests exist. The Functions in particular should have a suite exercising each send mode, park transition, and 24h window boundary.
  8. Secrets handling. API Key secret lives in the Functions environment. For production, rotate via infrastructure-as-code and consider a managed secret store (AWS Secrets Manager, GCP Secret Manager) if the deployment is multi-tenant.
  9. Harden the window UX. The toast fires on any WA send failure, not strictly on wa_window_closed (the error body is stripped by the time it reaches the browser). Tighten the match when Flex surfaces the richer error payload, or add a secondary fetch to confirm before prompting.

API Surface

Reference Endpoints

All plugin-facing endpoints are Flex-token-gated. /conversation-lifecycle is .protected.js, so the Serverless runtime verifies Twilio's request signature on every invocation. /wa-window-pre-webhook is not currently signature-validated — a production hardening would rename it to .protected.js or add explicit signature verification in-handler.

Endpoint Called By Responsibility
/list-templates Plugin on tab mount Fetches approved WhatsApp templates from the Content API (v2 ContentAndApprovals) and extracts variable keys.
/send-outbound-template Plugin (Send & open chat) Creates conversation, participant, lifecycle webhook, template message, and a Flex Interaction with worker_sid targeting the sender.
/send-outbound-notask Plugin (Reply to me / Reply to queue) Creates conversation + template; sets sendMode on conversation attrs. No task yet — the lifecycle webhook spawns it on first reply.
/reopen-conversation Plugin (Reopen button) Creates a Flex task against the existing conversation. Reuses the Interaction channel via channels.invites.create.
/park-conversation Plugin (Park buttons, window-closed toast) Closes the agent participant, updates conversation attrs with the chosen reply mode, moves the Sync row to the parker, refreshes Timers.Closed.
/verify-active Plugin on panel mount Sweeps the agent's Sync rows against Twilio and deletes any whose conversation is closed. Self-heals drift.
/sync-token Plugin Mints a short-lived Twilio Access Token with a Sync grant for the agent's identity.
/conversation-lifecycle (protected) Twilio Conversations (per-conversation webhook) On onMessageAdded from the customer: spawns task via Interactions or raw TaskRouter. On onDeliveryUpdated: patches Sync status. On onConversationStateUpdated: closed: deletes Sync rows.
/wa-window-pre-webhook Twilio Conversations (service pre-webhook) Rejects WA free-text sends outside the 24h window with HTTP 403 wa_window_closed. Fast-paths non-WA, inbound, template sends, and non-plugin conversations.
